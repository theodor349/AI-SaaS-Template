# User readiness and webhook transactions

Authentication (#2), user synchronization (#3), billing (#4), and account cleanup (#5) share a boundary: an authenticated identity can exist before its application record. `users.current` derives the caller from `requireIdentity` and returns `provisioning`, `ready`, or `deleting`. Anonymous calls fail with `UNAUTHENTICATED`; missing records do not mean sign-out. Mount auth-dependent consumers below Convex authentication readiness. The [provisioning component](../../components/UserProvisioning.tsx) calls `users.ensureCurrentUser` after authentication settles and offers retry on failure; it is mounted inside the official Clerk provider. The action fetches the verified identity from Clerk's Backend API, so local sign-in needs no webhook tunnel. Explicit reconciliation uses `users.ensureCurrentUser({ refresh: true })` to fetch a fresh profile even when already ready. A ready record grants no paid access: #4 must independently enforce its paid-entitlement contract.

[Profile synchronization](../../convex/users.ts) patches only its own fields. Billing may extend the user schema without having its entitlement reset by profile delivery or provisioning. Provider IDs and arbitrary lookup remain internal; account features should use the identity-derived current-user API.

## Adding another provider

Register the verified HTTP adapter in [convex/http.ts](../../convex/http.ts). Clerk verifies the original body with `svix-id`; Polar must verify its original body and use `webhook-id`. The adapter validates required fields before calling an internal mutation. That mutation calls [processDelivery](../../convex/webhooks.ts) with the provider namespace, an internal business-mutation reference, and its arguments. The shared processor invokes that handler through `ctx.runMutation`. The nested mutation is intentional: its writes roll back on failure while the outer transaction records a retryable failure.

Database effects and successful completion commit in one serializable transaction. Simultaneous deliveries serialize on the indexed tracking key. A crash before commit rolls everything back; a lost HTTP response after commit is safe to redeliver. There are no persisted processing locks, leases, or workers that need recovery. Successful duplicates return 200; failures return 503 and rely on provider redelivery. Unknown valid types are deliberately acknowledged. Bad signatures and malformed required payloads return 400 without domain writes. Logs carry delivery context and fixed failure codes, never raw provider errors or profiles.

Delivery history expires 30 days after the last attempt; a bounded cron removes it and logs unresolved failures. Tracking therefore cannot provide permanent business idempotency. Each domain handler must also use durable resource IDs, revisions, or monotonic transitions. Clerk keeps `updated_at` plus event timestamp to reject stale updates and retains terminal identity tombstones across tracking expiry. Billing must apply the same principle to resource updates. External side effects require a transactional outbox/durable workflow and provider idempotency keys; do not execute them inside this database-only processing handler.

## Deletion handoff

Clerk deletion atomically marks the application user `deletion_requested` and creates one [account lifecycle request](../../convex/accountLifecycle.ts), including when the user did not previously exist. #5 owns the processor: consume pending requests, perform resumable cleanup, and atomically mark completion plus user lifecycle `deleted` when finished. Retain the user record until cleanup finishes and retain its minimal identity tombstone afterward. Neither replay nor a snapshot fetched before deletion can reactivate that Clerk ID; a genuinely new registration has a new provider ID.

Configure `CLERK_JWT_ISSUER_DOMAIN`, `CLERK_SECRET_KEY`, and `CLERK_WEBHOOK_SIGNING_SECRET` on the Convex deployment. Hosted Clerk endpoints use the deployment's Convex HTTP `/webhooks/clerk` URL for `user.created`, `user.updated`, and `user.deleted`. Bootstrap supplies a worktree-local signing secret when none is provided, including with `--no-polar`; it does not register a hosted endpoint. Signed HTTP tests use this isolated secret. Never point a hosted endpoint at a generated local secret unless an explicit development forwarder uses it.
