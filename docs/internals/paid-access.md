# Paid access and provider recovery

Authentication and paid access have separate boundaries. Account provisioning, billing recovery, profile controls, and sign-out remain available without Pro. Paid application functions use [requirePro](../../convex/lib/billing.ts); queries use materialized expiry maintained by durable scheduled mutations, while mutations also check the deadline at execution. New paid features must use this same guard. [PaidBoundary](../../components/billing/paid-boundary.tsx) prevents the UI from mounting paid consumers while readiness or entitlement is absent; it cannot replace backend authorization.

[Polar webhooks](../../convex/http.ts) verify the original body with the pinned SDK and validate the resource association. They commit a reconciliation request through the shared delivery processor. Their payloads never directly grant access. [Reconciliation](../../convex/polar.ts) reads current provider resources, and [billing state](../../convex/billingState.ts) publishes only a current leased snapshot. Permanent order/subscription IDs and supersession survive delivery retention.

Two entitlement rules are easy to get wrong. Past-due state ends access without grace; owners recover payment through the portal or checkout. Lifetime purchases permanently supersede prior recurring subscriptions, even if the lifetime order is later refunded, so an older subscription cannot become an accidental recovery plan. [Billing tests](../../convex/billing.test.ts) cover the remaining order, cancellation, and refund rules.

Customers use a worktree-scoped external identity derived from the authenticated token identifier. Email equality never proves ownership. Customer/order events before signup are retained unclaimed; a later verified external-ID association or owner reconciliation claims them. Missing external IDs must be repaired in Polar with the trustworthy application identity. `billing.recoveryIssues` exposes unclaimed customers, failed reconciliation, and recurring cleanup. Immediate retries are bounded, and the scheduled sweep continues recovery with capped hourly backoff. Provider failures cannot silently mark cleanup complete. Account deletion calls `polar.cleanupAccount` and retries false results or failures before finishing; it checks Polar even when the local customer linkage was missing.

`WORKTREE_ID` is the deployment's billing namespace. Changing it or the product IDs on a live deployment requires reconciling existing associations; don't reuse another deployment's namespace. Foreign worktree resources are ignored before creating domain or retry records. Renewals, refunds, and cleanup remain tied to the scoped customer, rather than trusting order metadata to survive every provider event.
