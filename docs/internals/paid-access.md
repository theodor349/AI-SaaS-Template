# Paid access and provider recovery

Authentication and paid access have separate boundaries. Account provisioning, billing recovery, profile controls, and sign-out remain available without Pro. Paid application functions use [requirePro](../../convex/billing/lib.ts); queries use materialized expiry maintained by durable scheduled mutations, while mutations also check the deadline at execution. New paid features must use this same guard. `requirePro` only checks the caller; a decision about another user, such as a limit on something they share, uses `hasPaidPro` from the same file, which applies the same expiry rule without throwing and ignores legal acceptance. [PaidBoundary](../../components/billing/paid-boundary.tsx) prevents the UI from mounting paid consumers while readiness or entitlement is absent; it cannot replace backend authorization.

[Polar webhooks](../../convex/http.ts) verify the original body with the pinned SDK and validate the resource association. They commit a reconciliation request through the shared delivery processor. Their payloads never directly grant access. [Reconciliation](../../convex/billing/polar.ts) reads current provider resources, and [billing state](../../convex/billing/state.ts) publishes only a current leased snapshot. Permanent order/subscription IDs and supersession survive delivery retention.

`billingAccounts` holds only the customer link and the published entitlement, because `billing.status` and `requirePro` subscribe to it from every paid page. Leases, retries, timed checks, and delivery tracking live in `billingSync`, and failures reach the billing page through the separate `billing.syncStatus` query. The operation lock that serializes checkout and subscription changes lives in `billingOperations`, one per user, so it can be taken before a first checkout creates the Polar customer. Write the entitlement row only when the projection changes; each write bumps `revision`. The billing page confirms a subscription change by waiting for a newer revision that matches the request, so `changeSubscription` bumps the revision itself when reconciliation published nothing new, such as cancelling an already cancelled renewal.

Two entitlement rules are easy to get wrong. Past-due state ends access without grace; owners recover payment through the portal or checkout. Lifetime purchases permanently supersede prior recurring subscriptions, even if the lifetime order is later refunded, so an older subscription cannot become an accidental recovery plan. The pure [computeEntitlement](../../convex/billing/entitlement.ts) and its [tests](../../convex/billing/entitlement.test.ts) cover the remaining order, cancellation, and refund rules; billing state only loads and persists around it.

Customers use a worktree-scoped external identity derived from the authenticated token identifier. Email equality never proves ownership. Customer/order events before signup are retained unclaimed; a later verified external-ID association or owner reconciliation claims them. Missing external IDs must be repaired in Polar with the trustworthy application identity. `billing.recoveryIssues` exposes unclaimed customers, failed reconciliation, and recurring cleanup. Provider failures cannot silently mark cleanup complete. Account deletion calls `polar.cleanupAccount` and retries false results or failures before finishing; it checks Polar even when the local customer linkage was missing. Final cleanup deletes and anonymizes the Polar customer. Polar allows one customer per email in an organization, so a kept customer would make checkout fail for the same person's next account, which gets a new external ID. Polar keeps a deleted customer's orders and still delivers events for it, so reconciliation treats a missing customer as one with no live subscriptions instead of a failure.

Webhooks, billing actions, account cleanup, and the expiry job at `paidThrough` each request an immediate reconciliation. Each one costs several Polar calls and lists up to 1000 orders, so timed checks are limited to accounts where something can change without a delivered event. Active accounts get a daily safety check for lost refund, revocation, or renewal-flag events. A live subscription without paid time is waiting on a renewal or dunning payment; it is checked hourly during the first day after payment became due, then daily, until Polar ends it. Other ended or unpaid accounts have no timer: a purchase produces a webhook, and checkout reconciles first. A failed reconciliation retries itself with exponential backoff eight times, then the sweep retries it hourly. The per-minute sweep pages through every due account and reschedules itself until it has caught up, so the number of accounts sets its work rather than a fixed per-run limit.

One Polar access token, and its organization's rate limit, serves every user. [Rate limits](../../convex/rateLimits.ts) protect it. A signed-in action calls `admit` before its first provider request, which applies a per-user bucket and admits Polar actions only while half of the app's Polar budget remains. Internal work calls `spendPolar`, which counts its requests without refusing them, so webhook reconciliation and withdrawal refunds keep that half when users are busy. A new Polar call belongs under one of the two, or user traffic can crowd out refunds that have a legal deadline.

`WORKTREE_ID` is the deployment's billing namespace. Changing it or the product IDs on a live deployment requires reconciling existing associations; don't reuse another deployment's namespace. Foreign worktree resources are ignored before creating domain or retry records. Renewals, refunds, and cleanup remain tied to the scoped customer, rather than trusting order metadata to survive every provider event.
